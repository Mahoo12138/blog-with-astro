terms:
  ELF: Executable and Linkable Format，Linux/Unix 常用的目标文件、可执行文件与共享库格式，包含头、节、程序头、符号与重定位等结构。
  PE: Portable Executable，Windows 的映像文件格式；COFF 是相关的目标文件与符号格式。
  ABI: Application Binary Interface，二进制应用程序接口。约定函数参数、返回值、寄存器、栈对齐和数据布局等机器级规则。
  ASLR: Address Space Layout Randomization，地址空间布局随机化。随机改变映像、库、栈等区域的位置，降低地址预测的可靠性。
  PIE: Position-Independent Executable，位置无关可执行文件。支持主程序映像在可变基址加载，常与 ASLR 配合。
  PLT: Procedure Linkage Table，过程链接表。部分 ELF 动态链接构建用它作为外部函数调用的跳转入口。
  GOT: Global Offset Table，全局偏移表。ELF 动态链接中保存运行时地址或相关偏移的常见表结构。
  IAT: Import Address Table，导入地址表。PE 加载时由加载器解析并填入 DLL 导入函数地址的表。
  CRT: C Runtime Library，C 运行库。提供标准库函数、运行时状态，以及通常先于 main 执行的启动与退出代码。
  UCRT: Universal C Runtime，微软提供的通用 C 运行库，包含 printf 等 C 标准库函数的实现。
  glibc: GNU C Library，Linux 上广泛使用的 C 运行库实现，提供标准 C 库函数和一些系统接口封装。
  stdout: C 语言标准输出流。它可能连接终端、文件或管道，所以 stdout 不等于屏幕。
  syscall: 系统调用。用户态程序请求内核提供服务的受控接口；普通库函数不必然等于系统调用。
  RIP: 指令指针寄存器，指向当前指令流的位置。RIP 相对寻址以指令结束后的地址为基准计算目标。
  RDI: Linux x86-64 System V ABI 中传递第一个整数或指针参数的寄存器。
  RSP: Stack Pointer，栈指针寄存器，通常指向当前栈顶。
  RBP: Base Pointer / Frame Pointer，基址 / 帧指针寄存器。标记当前函数的栈帧，优化构建可能省略。
  RAX: x86-64 的通用寄存器之一，常用于返回值与临时数据。
  ISA: Instruction Set Architecture，指令集架构。定义处理器指令、寄存器和机器级行为的程序员可见规范。
  AST: Abstract Syntax Tree，抽象语法树。编译器用树形结构表达源代码语法关系的内部表示。
  IR: Intermediate Representation，中间表示。源语言与目标机器指令之间的中间程序形式，便于优化和转换。
  relocation: 重定位记录。告诉链接器要修补哪个字段、引用哪个符号、按什么规则计算新值。
  mnemonic: 汇编助记符。机器指令的可读名称，例如 mov、lea、call、ret。
  opcode: 操作码。机器指令编码中表示操作类别的部分，例如 x86-64 近相对 call 通常以 E8 开头。
  displacement: 位移量。相对某个基准地址的差值；RIP 相对寻址和近相对 call 都会使用位移。
  pagefault: 缺页异常。CPU 检测到页面访问需要内核处理时发生的异常，可能是正常的按需调页。
  libc: C 标准库实现的常见统称；Linux 上经常指 glibc，但并非所有系统都使用它。
  DLL: Dynamic-Link Library，动态链接库。Windows 上可由多个程序在运行时加载和共享的代码/数据模块。
  COFF: Common Object File Format，与 Windows 工具链相关的目标文件及符号格式。
  GCC: GNU Compiler Collection，GNU 项目的编译器工具集合，通常由驱动程序协调预处理、编译、汇编和链接。

## 起点：C 源代码到底表达了什么？

为了明确边界，我们使用一个足够小、但符合标准 C 程序结构的示例。最后的输出故意没有换行符。

#include <stdio.h>

    printf("hello world");
    return 0;

</Card>

## 点击“编译”：构建系统启动了一条工具链

编辑器里的“运行”按钮通常负责组织命令、显示日志和启动进程；真正解析 C 代码的是编译器工具链，而不是 IDE 的按钮本身。

<Grid cols={3}>
<Tile label="EDITOR / IDE" title="发起构建请求">读取任务配置、工作目录、环境变量和编译参数，然后启动外部工具进程。</Tile>
<Tile label="COMPILER DRIVER" title="工具链调度器">例如 GCC 的 <code>gcc</code> 驱动程序，按目标平台和参数调用预处理器、编译器、汇编器与链接器。</Tile>
<Tile label="OPERATING SYSTEM" title="创建工具进程">操作系统装载编译器可执行文件、建立它的虚拟地址空间并调度 CPU 执行它；之后同样的 OS 还会执行生成的程序。</Tile>
</Grid>

<Callout type="info">**构建期与运行期：** GCC/Clang/MSVC 是生成程序的工具；`hello` / `hello.exe` 是稍后运行的程序。编译器进程退出不代表目标程序也运行过了。</Callout>

<Card title="编译器内部：从字符到指令选择">
<Grid cols={3}>
<Tile label="FRONT END" title="词法、语法与语义">把字符序列切成 token，按 C 文法构造语法结构，再检查类型、声明、参数匹配等语言规则。错误会以诊断信息报告。</Tile>

<Tile label="BACK END" title="指令选择与寄存器分配">把 IR 映射到目标 ISA，分配寄存器、安排指令和栈布局，最后输出汇编文本或直接输出机器码。具体内部结构取决于编译器实现。</Tile>

## 编译：C 语句如何变成汇编指令？

不要先背汇编。先把它当作“把一个 C 语句拆成处理器能完成的小动作”的记录，再逐条看每个动作为什么出现。

<Intro><strong>我们究竟在观察什么？</strong> 下面采用一次 GCC 14.2.0、x86-64 Linux、未开启优化（<code>-O0</code>）的示例输出。C 语言标准只规定程序的含义，并不规定必须生成这些指令；换编译器、优化等级或平台后，汇编可以不同，但“把字符串地址作为参数交给 <code>printf</code>”这个意图不变。</Intro>

### 先认识汇编里的基本积木

<Grid cols={3}>
<Tile title="1. 指令与助记符"><code>mov</code> 表示搬运数据，<code>lea</code> 计算地址，<code>call</code> 调用函数，<code>ret</code> 返回。它们是机器指令的可读名字；CPU 最终读取的是相应的字节编码。</Tile>
<Tile title="2. 寄存器 Register"><code>RAX</code>、<code>RDI</code>、<code>RSP</code>、<code>RBP</code> 是 CPU 内部的小型高速存储位置。它们可以暂存数据、参数、栈地址或返回值，不是内存中的变量名。</Tile>
<Tile title="3. 操作数 Operand">例如 <code>mov rdi, rax</code> 的两个操作数都是寄存器。<code>[rip+0x123]</code> 表示按地址计算规则访问内存；<code>lea</code> 使用类似写法时，是计算有效地址而不读取那个地址里的字符串内容。</Tile>
<Tile title="4. 标签与伪指令"><code>main:</code>、<code>.LC0:</code> 是标签，给代码或数据一个可引用的名字。<code>.text</code>、<code>.section</code>、<code>.string</code> 是给汇编器的组织指示，不是让 CPU 执行的指令。</Tile>
<Tile title="5. 代码区与数据区"><code>.text</code> 通常放机器指令；<code>.rodata</code> 是 read-only data（只读数据）的惯用 section 名，常放字符串常量。指令与数据都是字节，但它们的用途不同。</Tile>
<Tile title="6. 函数调用约定">调用者与被调用函数必须约好参数放在哪、返回值放在哪、哪些寄存器需要保存。这套机器级规则属于 <code>ABI</code>；本例按 Linux x86-64 System V ABI 解释。</Tile>
</Grid>

<Callout type="warn">**先别把“只读数据区”想成一种神秘硬件。** `.rodata` 首先是目标文件里一个有名字的 section（节），用于告诉汇编器和链接器“这部分是只读数据”。链接器随后通常把它放进运行时不可写的加载段。section 是组织文件内容的方式；segment（段）则描述装载器如何把内容映射进进程。它们相关，但不是同一个概念。</Callout>

### 这次编译器输出的汇编

```asm
.section .rodata            # 告诉汇编器：接下来是只读常量数据
.LC0:                       # 编译器给字符串起的内部标签
    .string "hello world"   # 11 个可见字符 + 结尾的 NUL 终止字节

.text                       # 接下来是机器指令所在的代码 section
main:                       # 函数入口标签
    push rbp                # 保存调用者的帧指针
    mov  rbp, rsp           # 用当前栈顶建立本函数的帧指针
    lea  rax, .LC0[rip]     # 算出字符串地址，放进 RAX
    mov  rdi, rax           # 按 Linux x86-64 ABI，把第一个参数放进 RDI
    mov  eax, 0             # 可变参数调用的 ABI 要求：AL 中向量参数数目为 0
    call printf@PLT         # 调用 printf 的 PLT 入口
    mov  eax, 0             # main 的返回值 0
    pop  rbp                # 恢复调用者的帧指针
    ret                     # 返回运行库启动代码
```

### 把 C 语句和汇编一一对上

<Caption>编译器不需要让每条 C 语句对应一条汇编指令。一行 C 代码可能变成多条指令；反过来，多条 C 语句也可能被优化成一段指令。这里是便于学习的“职责对应”，不是语言规范要求的固定映射。</Caption>

<Table>
<table>
<thead><tr><th>C 源代码 / 隐含工作</th><th>对应的汇编</th><th>这一步具体做了什么？</th></tr></thead>
<tbody>
<tr><td><code>"hello world"</code> 字符串常量</td><td><code>.section .rodata</code> · <code>.LC0:</code> · <code>.string "hello world"</code></td><td>给字符串分配一段数据空间，并设置内部标签 <code>.LC0</code> 方便其他指令引用。字符串末尾有一个 <code>00</code> 终止字节，它用于标记 C 字符串结束，不会作为可见字符打印。</td></tr>
<tr><td><code>printf("hello world");</code> 第 1 步：找到参数</td><td><code>lea rax, .LC0[rip]</code></td><td>计算字符串的地址并放入 <code>RAX</code>。这里的 <code>lea</code> 是“取有效地址”，不会把 12 个字符串字节塞进寄存器。</td></tr>

<Intro><strong>读这段汇编时的最小心智模型：</strong> <code>.rodata</code> 保存“要打印的内容”；<code>lea</code> 找到内容所在的地址；<code>mov rdi, rax</code> 按 ABI 把地址交给函数；<code>call</code> 转到函数入口。CPU 执行的是每条指令的机器码，标签和注释只是帮助汇编器 / 人类组织和理解程序。</Intro>

<Callout type="warn">**为什么 Windows 的汇编看起来会不同？** Windows x64 常用的前四个整数 / 指针参数寄存器是 `RCX`、`RDX`、`R8`、`R9`；Linux x86-64 System V 则使用 `RDI`、`RSI`、`RDX`、`RCX`、`R8`、`R9`。同一句 C 代码之所以可能生成不同指令，一部分原因就是目标平台的 ABI 不同。</Callout>

<Callout type="info">**优化会改变外观。** `-O0` 下保留帧指针、把地址先放入 `RAX` 再复制到 `RDI`，是本次构建的选择。`-O2` 可能减少指令、改变寄存器分配或省略帧指针；编译器不会承诺任何固定的汇编展开。</Callout>

<Caption>先记住一个模型：<strong>汇编器「留坑 + 记便签」，链接器「按便签填坑」。</strong>下面两条指令需要写“目标离我多远”，但编译 <code>hello.o</code> 时距离根本算不出来——字符串坐哪要等链接器排座位，<code>printf</code> 干脆在另一个文件里。汇编器不猜：把要写距离的 4 个字节先留成 0（<strong>坑</strong>），再在重定位表里记一张<strong>便签</strong>（“这里有个坑，按相对某某符号的规则填”）。链接器排好座位后逐条读便签、算距离、填坑。下面沿这两条指令，把坑和便签从 <code>hello.o</code> 一路追到最终 <code>hello</code>。</Caption>

<tr><td><code>4: 48 8d 05 00 00 00 00</code></td><td>偏移 <code>0x4</code> 起是一条 7 字节的 <code>lea</code>：前 3 字节是指令形式，后 4 字节是坑（位移字段，暂为 0）。坑从偏移 <code>0x7</code> 开始。</td></tr>
<tr><td><code>7: R_X86_64_PC32 .rodata-0x4</code></td><td>便签，不是指令。<code>0x7</code> = 坑的位置；<code>.rodata</code> = 相对谁；<code>PC32</code> = 填法（32 位相对位移）；<code>-0x4</code> = 基准修正量。</td></tr>
<tr><td><code>13: e8 00 00 00 00</code></td><td>同理：<code>e8</code> 是近相对 <code>call</code> 的 1 字节操作码，后 4 字节又是一个坑。<code>call 0</code> 不是真的调地址 0，只是距离还没填。</td></tr>
<tr><td><code>14: R_X86_64_PLT32 printf-0x4</code></td><td><code>call</code> 的便签：坑在 <code>0x14</code>（<code>0x13</code> + 1 字节操作码）；<code>printf</code> 是外部符号，<code>PLT32</code> 表示按“可指向 PLT 入口”的相对位移来填。</td></tr>
</tbody>
</table>
</Table>

<Subhead level={4}>第二步：便签怎么写？——三个问题和一条填数公式</Subhead>
<Caption>一张便签只回答三个问题：<strong>填哪里</strong>（offset，坑的字节位置）、<strong>相对谁</strong>（symbol，拿来算距离的目标）、<strong>怎么算</strong>（type + addend，规则和修正量）。把 <code>hello.o</code> 的两张便签集中打印：</Caption>

```text
Offset          Type               Symbol + Addend
000000000007    R_X86_64_PC32      .rodata - 4
000000000014    R_X86_64_PLT32     printf - 4
```

<Caption>填数规则一句人话：<strong>坑里要填的数 = 目标地址 − 下一条指令的地址</strong>。为什么是“下一条指令”？因为 x86 的 RIP 相对寻址就是以它为基准。写成公式里的字母就是 <code>S + A − P</code>：</Caption>

<Formula>人话：填入 = 目标地址 − 下一条指令地址（S −（P + 4））<br />公式：PC32 → S + A − P　·　PLT32 → L + A − P（其中 A = −4）</Formula>

<Subhead level={4}>第三步：链接器怎样按便签填坑？</Subhead>
<Caption>本次示例构建里，链接器把 <code>main</code> 排到 <code>0x1139</code>、字符串排到 <code>0x2004</code>，并为 <code>printf</code> 准备了 <code>0x1030</code> 处的 PLT 入口。座位定了，两张便签就能算了：</Caption>

```text
0000000000001139 <main>:
  1139: 55                    push rbp
  113a: 48 89 e5              mov rbp,rsp
  113d: 48 8d 05 c0 0e 00 00  lea rax,[rip+0xec0]  # 0x2004：字符串位置
  1144: 48 89 c7              mov rdi,rax
  1147: b8 00 00 00 00        mov eax,0
  114c: e8 df fe ff ff        call 0x1030 <printf@plt>
  1151: b8 00 00 00 00        mov eax,0
  1156: 5d                    pop rbp
  1157: c3                    ret
```

<Panes>
<Pane title="例子 A · 字符串的坑">
<p>坑在 <code>0x1140</code>（<code>lea</code> 开头 <code>0x113d</code> + 3 字节形式），下一条指令在 <code>0x1144</code>。代入公式：</p>
<Formula expr="0x2004 − 0x1144 = 0x0ec0" />
<Caption>结果按小端序（低字节在前）写进坑：<code>c0 0e 00 00</code>。执行时 RIP = 0x1144，<code>0x1144 + 0x0ec0 = 0x2004</code>，正好落在字符串上。</Caption>
</Pane>
<Pane title="例子 B · printf 的坑">
<p>目标 <code>printf@plt</code> 在 <code>0x1030</code>，下一条指令在 <code>0x1151</code>。代入公式：</p>
<Formula expr="0x1030 − 0x1151 = −0x121" />
<Caption>位移可正可负：这里为负，因为 PLT 排在 <code>main</code> 前面，要往回跳。<code>-0x121</code> 写进坑是 <code>df fe ff ff</code>（有符号 32 位、小端序）。执行时先落到 PLT 跳板，再由动态链接路径转到 libc 里的 printf。</Caption>
</Pane>
</Panes>

<Subhead level={4}>第四步：哪些坑不在链接时填？——运行时动态链接</Subhead>
<Caption><strong>链接时填的坑：</strong>字符串、<code>printf@plt</code> 这类目标在生成 <code>hello</code> 时座位已定，链接器按便签填完就不再改。</Caption>
<Caption><strong>运行时才填的坑：</strong><code>call</code> 的目标是 PLT 跳板，而不是 libc 里 printf 的真身——真身的地址要等进程启动、共享库加载后才知道。这些坑（例如 GOT 中的函数地址槽）由动态加载器按动态链接信息补填，具体方式随链接选项与安全设置变化。</Caption>

<Caption>三个角色处理的是三个时间点的地址问题：汇编时写不下的距离，链接时填映像内部的，启动时填跨共享库的。</Caption>
<Caption>这些偏移和字节是本次 GCC 14.2.0、x86-64 Linux、<code>-O0</code> 示例构建的具体结果，不是每台机器都固定如此。PIE、ASLR、链接器和构建选项都可能改变最终显示的地址。</Caption>

## 可执行文件并非“一团机器码”

ELF 和 PE 都有格式头、节 / 段信息、入口点、导入或动态链接信息等元数据。操作系统和加载器依靠这些结构理解文件。

<Grid cols={2}>
<Card title="Linux：ELF 结构">

```text
Class:       ELF64
Data:        little endian
Type:        DYN (PIE executable)
Machine:     x86-64
Interpreter: /lib64/ld-linux-x86-64.so.2
NEEDED:      libc.so.6
```

<Caption>ELF 头描述文件的基本属性。<strong>Section（节）</strong>是链接 / 调试时常用的逻辑组织（例如 <code>.text</code>、<code>.rodata</code>、<code>.symtab</code>）；<strong>Program Header（程序头）</strong>里的 <code>PT_LOAD</code> 等条目则描述运行时要映射的 segment。不要把“节”和“段”混为一谈。</Caption>
</Card>
<Card title="Windows：PE 结构">

```text
DOS header / DOS stub
PE signature
COFF File Header
Optional Header (PE32+)
Section Headers
  .text  · code
  .rdata · read-only data / imports
  .data  · initialized data
Import Table / IAT
Relocation data / other directories
```

<Caption>PE Optional Header 含有入口点的 RVA（相对映像基址的地址）和数据目录。导入表说明程序依赖哪些 DLL 和符号，IAT（导入地址表）提供运行时调用导入函数的地址槽位。节名有约定意义，但具体布局由链接器决定。</Caption>
</Card>
</Grid>

## printf 到底怎样让文字出现在屏幕上？

关键区别：C 标准库函数、操作系统系统调用和终端模拟器是三个不同层次。

先认识下文的 `fd 1`：fd 是**文件描述符**（file descriptor）——进程里一个代表“已打开的输出目标”的小编号，内核靠它认路；`1` 号固定是标准输出（stdout）。先把它当作“输出通道 1 号”：往 fd 1 写，就是往 stdout 当前指向的地方写。

## 把整条链路翻译成 Windows 10 的心智模型

Windows 上仍然有编译、汇编、链接、运行库、装载与输出，但不能直接把 Linux 的 ELF / ld-linux / glibc 细节套上去。

<Card>
<Grid cols={2}>
<Grid stack>
<Tile label="A / BUILD" title="MSVC 前端与 COFF 目标文件"><code>cl.exe</code> 预处理并编译 C 代码；常见中间产物是 <code>.i</code>、汇编列表和 <code>.obj</code>。目标文件中的外部引用通过符号表与重定位记录表达。</Tile>
<Tile label="B / LINK" title="LINK 解析导入并生成 PE">链接器把目标文件、启动库、CRT 库和导入库组合成 PE 映像。导入库通常提供链接期所需的符号 / DLL 导入描述，不必把整个 DLL 实现复制进 EXE。</Tile>
<Tile label="C / LOAD" title="Windows Loader 映射映像与 DLL">进程创建时，Windows 的映像加载路径解释 PE 头和节表，映射可执行映像、解析 DLL 依赖和导入地址，并处理必要的重定位。底层实现会随 Windows 版本变化。</Tile>
<Tile label="D / RUN" title="CRT 进入 main，再进入 UCRT 输出">常规控制台程序的 CRT 入口初始化运行库后调用 <code>main</code>。<code>printf</code> 经过 UCRT 的流和缓冲逻辑，将数据写往标准输出句柄；最终目标可能是控制台、文件或管道。</Tile>
</Grid>

<Subhead>调用约定差异：第一个参数放在哪里？</Subhead>

```asm
; Linux x86-64 System V ABI
lea  rdi, [rip + string]
xor  eax, eax
call printf@PLT

; Windows x64 ABI（概念示意）
lea  rcx, [string]
; 调用者通常还要预留 32-byte shadow space
call printf_import_thunk
```

<Caption>Linux System V x86-64 通常用 <code>RDI</code> 传第一个指针参数；Windows x64 通常用 <code>RCX</code>。Windows x64 调用约定要求调用者为被调函数预留 32 字节 shadow space。示意代码不代表某个 MSVC 版本的精确输出。</Caption>
<Callout type="warn">**不要把以下概念混为一谈：** PE 的 IAT 与 ELF 的 GOT 都可以参与动态地址解析，但结构、链接器约定及加载机制不是同一种格式；Windows 的 UCRT/WinAPI 也不等于 Linux 的 glibc/系统调用接口。</Callout>

## 如果出错，错误会在哪一阶段出现？

区分编译错误、链接错误、装载错误与运行错误，定位问题会容易很多。

<Grid cols={4}>
<Tile tone="danger" label="PREPROCESS / COMPILE" title="头文件找不到"><code>stdio.h</code> 找不到；或语法 / 声明检查失败。程序通常还没有生成目标文件。</Tile>
<Tile tone="danger" label="LINK" title="未定义引用">声明能通过编译，但最终链接找不到符号或导入库，例如 undefined reference / unresolved external。</Tile>
<Tile tone="danger" label="LOAD" title="无法执行或缺 DLL">文件格式 / 架构不匹配、权限不允许执行、动态加载器或依赖库找不到。</Tile>
<Tile tone="danger" label="RUNTIME" title="输出或退出异常">进程已启动，但可能因运行时错误、I/O 目标异常或退出前的异常路径而未按预期输出。</Tile>
</Grid>

## 如何在自己的机器上验证？

把这份页面当成路线图，实际运行工具查看真实构建产物。命令结果会随编译器、版本、架构和链接选项变化。

<Grid cols={2}>
<Card>

```bash
gcc --version
gcc -v hello.c -o hello
file hello
size hello
nm hello.o
readelf -h -l -S -d hello
readelf -r hello.o
objdump -drwC -Mintel hello.o
objdump -d -Mintel hello
strace -e trace=execve,write,exit_group ./hello
```

</Card>
<Card>

```powershell
cl /Bv
cl /nologo /Od /FAcs /c hello.c
dumpbin /headers hello.obj
dumpbin /symbols hello.obj
dumpbin /relocations hello.obj
dumpbin /disasm hello.obj
link /verbose hello.obj /out:hello.exe
dumpbin /imports hello.exe
dumpbin /headers hello.exe
```

</Card>
</Grid>

<Caption>Windows 部分命令需要 Visual Studio / Build Tools 的开发者命令提示符。Linux 的 <code>strace</code> 可能需要单独安装；系统调用跟踪展示的是某次运行的实际系统调用，不应将其误认为 C 语言标准保证的固定序列。</Caption>
